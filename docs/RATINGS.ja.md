# 調整済みプラスマイナス評価

「どのクラブ同士の試合か」を知っているうえで、さらに「誰がピッチにいるか」を知ると
どれだけ当たるようになるのか。このリーグでの答えは「少しだけ、ただし測れる量」です。

```
togakuren ratings --validate     # 下の表
togakuren ratings                # 選手一覧（手元のみ）
```

## 手法と、この出典が適している理由

Sæbø と Hvattum のプラスマイナス評価は、キックオフ・すべての交代・すべての退場で試合を
区間に切ります。区間の中ではピッチ上の22人が変わりません。応答はその区間で入った得失点差で、
出場している選手は自陣側なら +1、相手側なら −1 として、区間が1試合に占める割合を掛けて
回帰に入ります。リッジ罰則は、20分しか出ていない選手に20分ぶんのノイズを帰属させないための
ものです。

必要な入力はキックオフ、分つきの交代、分つきの退場、分つきの得点だけです。これはこの連盟が
記録しているものそのもので、イベントデータもトラッキングデータも、放送局が売るような素材も
要りません。出場時間を復元するために用意した `appearances.on_minute` / `off_minute` が
そのまま使えます。

2022〜2026年のリーグ戦で：

| | |
|---|---|
| 両チームとも先発11人が揃っている試合 | 1,569 |
| 照合を通った試合（後述） | **1,235** |
| 区間 | **8,087**（平均13.7分） |
| 選手 | 3,503人。うち270分以上は2,242人 |
| 会場からホームを特定できた区間 | 60% |

## 合計が合わない得点

分つきの得点イベントが記録スコアと一致するのは **1,569試合中1,235試合（79%）** です。
差はほぼすべて1点で、原因は連盟が得点者不明の得点とオウンゴールを、分つきのイベントではなく
試合レコード上の件数として持っていることにあります。

区間モデルは分の分からない得点を置く場所がありません。したがって照合を通らなかった試合は
黙って誤った採点をせず除外しています。除外数はコマンドが表示します。除外前の姿を見たい場合は
ライブラリ側の `segments(..., reconcile=False)` を使ってください。

## どれだけの価値があるか

この手法にはリッジ罰則が2つあり、それをどこで決めたかで数字の意味が変わります。全試合を使った
交差検証で罰則を選び、その同じ試合で交差検証のスコアを報告すれば、**選択がすでに見た試合で
採点している**ことになります。そこで以下の罰則は、採点対象の試合を一切見ない内側の交差検証で
**各分割の学習データの中だけで**選んでいます（`--tune`）。

試合単位のグループ5分割交差検証です。試合まるごとを取り置くので、テスト試合の区間が学習側に
混ざることはありません。誤差は区間予測を足し上げた**試合の得失点差**に対して測っています。

| モデル | MSE | zero比 |
|---|---|---|
| zero | 6.7676 | — |
| クラブのみ | 4.4652 | −34.0% |
| 選手のみ（クラブ項なし） | 5.0296 | −25.7% |
| **クラブ＋選手** | **4.2988** | **−36.5%** |

クラブに加えて選手を知ることの上乗せ: **+3.73%**。

この種の交差検証が測っているのは「そのシーズンをどれだけうまく**記述**できるか」であって
「先に持ち越せるか」ではありません。そこでより厳しい検証として、各シーズンの前60%の試合で
学習し、同じシーズンの残りを予測します（学習741試合・テスト494試合）。

| モデル | MSE | zero比 |
|---|---|---|
| zero | 6.7955 | — |
| クラブのみ | 4.4501 | −34.5% |
| 選手のみ（クラブ項なし） | 5.3796 | −20.8% |
| **クラブ＋選手** | **4.2696** | **−37.2%** |

上乗せは **+4.06%**。**厳しいほうの検証で数字が良くなる**ので、向きとしては正しく出ています。

```
togakuren ratings --validate --tune          # 上の表。約2分30秒
togakuren ratings --forward --tune           # 下の表。約20秒
```

**正直に測り直した代償は0.34ポイントでした。** 定数のままなら交差検証の値は+3.73%ではなく
+4.07%と読めます。差が小さい理由は選ばれた罰則に出ていて、選手側はどの分割でも20か30、
クラブ側は0.03〜0.3に収まりました。定数（30と0.1）は各分割が自力で選ぶ範囲の内側にいた、
ということです。これは良いほうのケースですが、**走らせるまで分かりませんでした。**

なお本文書の以前の版は、前方分割の上乗せを **+5.44%** と書いていました。これはこのパッケージに
手法を移す前のプロトタイプの数字で、**このコードでは再現しません**（分割が741/494ではなく
735/500で、値も戻ってきません）。辻褄を合わせるのではなく、実際に動くコードが出力する値へ
置き換えました。誰も再実行できない数字は根拠になりません。

ホームアドバンテージは同じ推定から **+0.26 得点/90分**。APIは会場を記録していてホストを
記録していないため、会場から推定しています。推定の方法と成功率は
[PREDICTION.ja.md](PREDICTION.ja.md) にあります。

## 間違えると結論が逆転する2点

**クラブ項と選手項には別々の罰則をかけること。** 50強のクラブにはほとんど収縮が要らず、
2,000人の選手には大量に要ります。選手に合わせた共通の罰則を両方にかけると、クラブ側が
過剰に収縮して、結合モデルがクラブ単独より**悪く**なります。そこで結論を出すと
「選手の情報には価値がない」という逆の答えになります。`Design.penalties` が2つを別に取るのは
このためです。

**正規方程式を作らないこと。** 列が数千あると行列は数百万要素になり、解くことよりも作ることが
律速になります。設計行列の各行の非ゼロは約23個なので、疎な行に対する共役勾配法で同じ答えに
到達します（テストで小さい問題の直接解法と一致することを確認しています）。純Pythonで数秒、
標準ライブラリのみという方針も維持できます。

## ここに無いもの

評価値そのものです。選手単位の値であり、対象はアマチュアの学生なので、`ratings` は
画面に出すだけでファイルには書きません。他のすべての選手単位の出力と同じ扱いです。
上の検証表は集計値で個人を含まないため、公開しているのはそちらだけです。
[DATA_POLICY.ja.md](DATA_POLICY.ja.md) を参照してください。

READMEにある2つの限界もここで繰り返しておきます。この出典ではPKをインプレーから分離できない
ため、PKを蹴る選手の得点も他の選手と同じようにこの数値に入っています。そして識別の情報源は
交代と退場です。**11人を固定して動かさないチームは、モデルに選手を分離する材料を与えません。**
その場合リッジ罰則は11人を同じ値の方向へ引き寄せます。
