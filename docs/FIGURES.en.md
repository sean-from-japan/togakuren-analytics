# Where the figures come from

*[日本語](FIGURES.ja.md)*

The twelve PNGs under `docs/figures/`, plus the two `docs/example-dashboard.*.png`
in the READMEs, are the only things in this repository that cannot be
regenerated by a single command. This says exactly what each one is a picture
of, so that a single figure can be replaced without guessing.

**There are two sets of the same six charts**, one per language, in
`docs/figures/en/` and `docs/figures/ja/`. The charts take every string they draw
from the page's payload, so `--lang` decides what the axes, legends and captions
say, and the English documents point at the English set. Club names are the
federation's own and are not translated in either set.

None of them is drawn by a plotting library. Every chart in this project is an
SVG built in the browser from the page's own JSON payload — see the `svg()`
helpers in `togakuren/trends.py` and `togakuren/dashboard.py` — which is why the
project has no dependencies. The PNGs are screenshots of those elements.

## What each file is

| file | page | element | chart |
|---|---|---|---|
| `fig-conversion.png` | `trends` | `#conv-line` | Conversion by division, season by season |
| `fig-grades.png` | `trends` | `#grades` | Year groups: share of minutes against goals per 90 |
| `fig-promotion.png` | `trends` | `#moves` | Points per game either side of a division change |
| `fig-trajectory.png` | `trends` | `#trajectory` | One club's path across levels — shot with `--club 430` |
| `fig-bubbles.png` | `dashboard` | `#bubbles` | League position against shot volume |
| `fig-fingerprints.png` | `dashboard` | `#radars` | Every club's six indices, side by side |
| `example-dashboard.en.png` | `dashboard` | the page itself | The README's screenshot: the page down to the first row of radars, shot at a 1160 × 1290 viewport |

## Regenerating one

```bash
togakuren trends --lang en --club 430 --out /tmp/trends.html
togakuren dashboard --lang en --privacy aggregate --out /tmp/dashboard.html
```

`--privacy aggregate` is not optional for the dashboard: it drops every
per-player view, so nothing that could end up in a committed image was ever
rendered.

Then, and this is the part that went wrong once:

**Shoot on the dark palette.** The page follows `prefers-color-scheme` and a
headless browser reports a light one, while every committed figure is dark. A
figure shot the other way puts the page's dark text colours on a white ground,
which is how `fig-promotion.png` shipped for a while with axis captions nobody
could read. Pin the palette before shooting by injecting the dark values from
`dashboard.CSS` onto `:root`, and check the result by looking at it.

Isolate the element named above — hide its siblings, all the way up to `body`,
rather than forcing `display` on the element itself, because `#radars` is a CSS
grid and forcing `display:block` on it collapses twelve radars into one. Crop
the flat background away, and **quantise to 256 colours**:

```bash
pngquant --force --output docs/figures/en/fig-bubbles.png 256 raw.png
```

That step is not cosmetic. These charts are flat colour, so 256 colours is
visually identical and roughly 60% smaller. PNGs do not delta-compress, so every
version of a figure that is ever committed stays in the history at full size.

## Two rules for changing a figure

**Only re-shoot when the picture changes.** Rewording a label in the document is
not a reason to replace the image, and neither is a language you are not
editing: the two sets are independent files. An earlier round of this project
left 13 blobs and 1.2 MB in the history for 7 files, 234 KB of it belonging to
files that had already been deleted and will never be reclaimed.

**Keep the dimensions.** The documents rely on the existing widths reading
sensibly at GitHub's content width; the sizes now in the tree are 564–1122 px
across.

## Why this is not automated

A headless browser would make these reproducible in CI, and that is a real
improvement that has not been made. It would also mean a browser download in the
test matrix for twelve images that change perhaps twice a year, in a project
whose whole point is that it runs on the standard library and nothing else. The
trade-off was decided in favour of the dependency-free rule, and this document
exists because that decision has a cost that should be written down rather than
discovered later.
